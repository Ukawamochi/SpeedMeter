# データ拡張の設計（docs/PLAN.md 第4段階 4-2）

実装は `src/spkrate/data/augment.py`、テストは `tests/test_augment.py`、
実測は `scripts/benchmark_augment.py`。

docs/spec.md が許す拡張は次の5種である。

> 時間伸縮0.7〜1.5倍（音程保持、モーラ数は不変）、雑音重畳SNR0〜20dB、合成残響、
> 音量変化、帯域制限。時間方向のマスクは正解と矛盾するため禁止

## 0. 決めたことの一覧

| 項目 | 決定 |
| --- | --- |
| 適用する対象 | **波形**（16kHzモノラル float32）。メルは拡張後に計算し直す |
| 事前計算特徴量（18.4GiB）の使い道 | **拡張しない経路**（検証・評価、拡張なしの対照実験、正規化値の算出） |
| 特徴量に直接かける拡張 | 周波数方向のマスクのみ（`frequency_mask`）。時間方向のマスクは実装しない |
| 時間伸縮の手段 | 位相ボコーダ（`librosa.stft` → `librosa.phase_vocoder` → `librosa.istft`、n_fft=1024、hop=256） |
| 雑音 | MUSAN の **noise サブセットのみ**。speech は使わない（拒否する） |
| 残響 | pyroomacoustics の直方体部屋。RT60 0.1〜0.7秒、寸法 3〜10m × 3〜10m × 2.3〜4.0m |
| ラベル | モーラ数はどの拡張でも不変。毎秒モーラ数のみ時間伸縮で `÷ stretch` |

## 1. 拡張は波形に適用する

### 理由

時間伸縮・雑音重畳・残響・帯域制限はいずれも波形上の演算であり、
対数メルスペクトログラム（位相を捨てた実数のパワー表現）からは実行できない。

- 時間伸縮: 位相ボコーダは位相を必要とする。メルの時間軸を引き伸ばす代替案もあるが、
  それは「同じ音をゆっくり喋った」音ではなく「同じスペクトルを引き伸ばした絵」であり、
  実際のゆっくりした発話（定常部だけが伸び、破裂や摩擦の長さはあまり伸びない）とは違う
- 残響・帯域制限: どちらも線形フィルタで、メル上では周波数ビンをまたぐ畳み込みになる。
  近似はできるが近似でしかない
- 雑音重畳: 電力の加算はメル上でも近似できるが、位相の干渉を無視することになる

唯一メル上で正確に実行できるのは音量変化（対数メルでは定数の加算）だが、
そのためだけに経路を分ける利点は無い。

### 再計算のコスト（実測）

`uv run python scripts/benchmark_augment.py --clips 30`（train から等間隔に30件、
平均音声長3.894秒、1プロセス、CPU）。1クリップあたりのミリ秒。

| 処理 | 平均 | 中央 | 最大 |
| --- | ---: | ---: | ---: |
| mp3の復号と16kHzへの再標本化（`load_audio`） | 0.92 | 0.90 | 1.89 |
| 時間伸縮（stretch=1.3） | 4.86 | 4.61 | 11.67 |
| 残響: インパルス応答の生成 | 1.41 | 0.74 | 20.48 |
| 残響: 畳み込み | 0.46 | 0.38 | 1.27 |
| 雑音重畳（MUSAN読み出しを除く） | 0.05 | 0.04 | 0.10 |
| 帯域制限 | 0.91 | 0.88 | 1.67 |
| 音量変化 | 0.02 | 0.02 | 0.03 |
| `augment_waveform` ひとそろい（既定の適用確率） | 3.37 | 3.34 | 9.93 |
| **対数メルの再計算** | **0.32** | **0.29** | 0.51 |
| （比較）事前計算済み float16 シャードの読み出し | 0.28 | 0.30 | 0.47 |

**メルの再計算は1クリップ0.32ミリ秒**であり、事前計算済み特徴量を memmap から
読み出すコスト（0.28ミリ秒）と**ほぼ同じ**である。つまり「事前計算しておく」ことの
利点は、この工程に関してはほぼ無い。波形経路全体（読み込み0.92＋拡張3.37＋メル0.32）
でも約4.6ミリ秒／クリップで、train 236,143クリップなら1プロセスで約18分、
DataLoader を8ワーカーで回せば1エポックあたり約2.3分ぶんのCPU仕事にしかならない。
mps での学習1エポックがこれより短くなることは考えにくいので、
**拡張の有無にかかわらず入力側が律速にはならない**と判断する。

最も重いのは時間伸縮（4.9ミリ秒）だが、既定の適用確率0.5で、
しかも `augment_waveform` の実測（3.37ミリ秒）に織り込み済みである。

### 事前計算特徴量（18.4GiB）との使い分け

| 用途 | 経路 |
| --- | --- |
| 学習（拡張あり） | 波形を読む → `augment_waveform` → `log_mel_spectrogram` → 正規化 → `augment_feature`（周波数マスク） |
| 学習（拡張なしの対照実験） | `data/processed/features/train` を読む |
| 検証・評価 | `data/processed/features/dev` を読む（評価に拡張はかけない） |
| 正規化の平均・標準偏差 | `configs/normalization.yaml`（train の事前計算特徴量から算出済み。**拡張後の統計では再計算しない**。docs/spec.md「学習データ全体から算出した平均と標準偏差を固定値として使う」） |

**拡張済み特徴量を別途作り置きすることはしない**。拡張は毎エポック違う値を引くことに
意味があり、作り置きすると多様性がエポック間で固定される。容量も、1条件あたり
16.4GiB（train相当）が追加で必要になる。再計算コストが上のとおり無視できる以上、
作り置きの利点は無い。

なお、拡張ありの学習では `data/processed/features/train` は使わないが、
**削除しない**（対照実験と正規化値の出所として残す。CLAUDE.md の data/ の扱いにも従う）。

## 2. 各拡張のパラメータ範囲と既定の適用確率

`AugmentConfig` の既定値。適用順は「時間伸縮 → 残響 → 雑音重畳 → 帯域制限 → 音量変化」で、
収録の経路（部屋で響いた音に周囲の雑音が混ざり、伝送路で帯域が制限され、
最後に録音利得がかかる）に合わせてある。各拡張は独立に判定する。

| 拡張 | 既定の適用確率 | パラメータ範囲 | 出所 |
| --- | ---: | --- | --- |
| 時間伸縮 | 0.5 | 長さの倍率 0.7〜1.5（一様） | docs/spec.md の明示 |
| 残響 | 0.3 | RT60 0.1〜0.7秒、部屋 3〜10 × 3〜10 × 2.3〜4.0 m | 下の5節 |
| 雑音重畳 | 0.5 | SN比 0〜20dB（一様）、MUSAN noise | docs/spec.md の明示 |
| 帯域制限 | 0.25 | 下側遮断 0〜300Hz、上側遮断 3400〜7800Hz、バターワース4次 | 下記 |
| 音量変化 | 0.5 | 利得 −12〜+6dB（振幅が0.99を超えないよう抑える） | 下記 |
| 周波数方向のマスク | 0.5 | 帯を2本まで、1本あたり幅0〜12（80メル中）、埋める値0 | 下記 |

確率の考え方。**時間伸縮は話速そのものを変えるので最も効く拡張**であり、
学習データの毎秒モーラ数の分布を広げる唯一の手段でもある（Common Voice の
毎秒モーラ数は狭い範囲に集まっており、docs/spec.md の評価は8以上の帯まで求めている）。
雑音と音量はブラウザでの実使用に直結するので同じく0.5。
残響と帯域制限は、かかると音の性質が大きく変わるうえ計算も重い側なので低めにした。
これらは**暫定値**であり、根拠となる測定はまだ無い。第5段階以降に検証セットで
比較して見直す（対照実験は `AugmentConfig().disabled()` で行える）。

補足。

- 帯域制限の上側 3400Hz は電話帯域、7800Hz はほぼ無加工に相当する。
  下側 300Hz までを削るのは、小型マイクの低域不足を模すため。
  零位相フィルタ（`sosfiltfilt`）なので群遅延が無く、発話の時刻がずれない
- 音量変化は −12〜+6dB。上側を小さくしてあるのは、振幅を超過させないため利得を
  抑える処理が働くと実効的な利得が指定値と変わるからである
- 周波数方向のマスクは、正規化後の特徴量に0（＝平均）を埋める前提の既定値である

## 3. 時間伸縮の実装手段と、音程が保たれることの確認

### 手段: 位相ボコーダ

`librosa.stft`（n_fft=1024、hop_length=256）→ `librosa.phase_vocoder` →
`librosa.istft`（`length` を指定）という並びで実装した。標本化周波数を変えずに
STFTフレームの読み出し位置だけを変えるので、**音程（基本周波数・フォルマント）は変わらない**。

- **再標本化は使わない**。長さを `stretch` 倍にすると音程が `1/stretch` 倍にずれ、
  声の高さまで変わってしまう。これは話速の手掛かりとは別の変化であり、
  学習データに入れたい変動ではない
- **WSOLA（波形の重ね合わせ）も候補**だった。破裂音の立ち上がりが鋭く保たれる利点があるが、
  依存（`pyrubberband` は外部コマンド rubberband が必要、`audiotsm` は新規依存）が
  増える。librosa は既に依存にあり追加が不要なので、まず位相ボコーダを採る
- 分析窓は **1024点（64ミリ秒）** とした。librosa の既定2048（128ミリ秒）は
  音節の立ち上がりを鈍らせるため短くしてある。これは伸縮の内部パラメータであり、
  docs/spec.md の特徴量（n_fft=400、hop_length=160）とは無関係である
- `librosa.effects.time_stretch` をそのまま呼ばない理由: 内部の
  `np.arange(0, n_frames, rate)` が浮動小数の累積誤差で `n_frames` に届く長さがあり、
  `ParameterError: t_out values must be in the range [0, D.shape[-1])` で落ちる
  （librosa 1.0.0、実データのクリップで実際に発生した）。読み出し位置を自分で作って弾いている。
  副作用として出力長が `round(len(samples) * stretch)` に**厳密に**一致する

### 音程が保たれることの確認方法

`tests/test_augment.py::test_time_stretch_preserves_pitch`。
440Hzの正弦波を 0.7倍・1.5倍に伸縮し、振幅スペクトルの最大値をとる周波数が
**440Hz ± 5Hz** に留まることを確かめる（実測 440.0Hz）。
同じテストの中で、比較のために再標本化で長さを変えた場合を計算し、
そちらは 440Hz から20Hz以上ずれることも確かめている（採らなかった方式との対比）。

### ラベルとの関係（コードとテストで明示）

```
伸縮率 stretch（= 長さの倍率）に対して
    音声長      : duration * stretch
    モーラ数     : 不変                 ← mora_count_after_time_stretch
    毎秒モーラ数 : mora_per_second / stretch  ← mora_per_second_after_time_stretch
```

`stretch = 0.7` なら音声は0.7倍の長さに縮み（速口になり）、毎秒モーラ数は 1/0.7 = 1.43倍になる。
`AugmentResult.mora_count` / `AugmentResult.mora_per_second` が呼び出し側の窓口である。

## 4. MUSAN の雑音ファイルの選び方

**noise サブセットのみを使う。**

- **speech は使わない**。別話者の発話が混ざると、その話者が発したモーラが
  入力には存在するのに正解のモーラ数には含まれない。**入力と正解が矛盾する**ので、
  時間方向のマスクを禁じているのと同じ理由で除外する。
  `MusanNoiseSource` は `subsets` に `"speech"` を渡された時点で `ValueError` を投げる
  （`tests/test_augment.py::test_musan_source_rejects_speech_subset`）
- **music は当面使わない**。歌入りの曲には人声が含まれ、speech と同じ問題が起きる。
  器楽のみを選別すれば使えるが、選別には試聴が必要で CLAUDE.md が禁じている。
  また `data/musan/` には現在 **noise サブセットしか配置されていない**（935ファイル、
  data/DATASETS.md）ので、そもそも手元に music は無い。
  実装上は `ALLOWED_SUBSETS = ("noise", "music")` として将来の切り替え口だけ残し、
  既定は `("noise",)` にしてある
- 対象は `data/musan/noise/**/*.wav`（free-sound 843件、sound-bible 87件、計930件）。
  いずれも16kHzモノラルなので再標本化は起きない
- 1ファイルが必要な長さに満たなければ繰り返し、長ければ無作為な位置から切り出す
  （`fit_noise`）。復号した波形はファイル単位で最大64件まで保持して使い回す
- `data/musan/` は**読み取りのみ**。書き込み・削除は一切しない

SN比は全区間の実効値で定義する（`10*log10(信号の電力/雑音の電力)`）。
0dBでは雑音が無音区間を埋めて、包絡からは音節の塊が数えられなくなるが、
**実際に発話されたモーラの数は変わらない**ので正解ラベルは不変のままでよい。
聞き取りにくい入力を作ることが拡張の狙いである。

## 5. 残響のインパルス応答の生成条件

`generate_rir`（pyroomacoustics の `ShoeBox`）。1回の呼び出しで応答を1つ作る。

| 項目 | 値 | 理由 |
| --- | --- | --- |
| 部屋の形 | 直方体（ShoeBox） | 家庭・オフィス・教室を模す。任意形状は計算が重く、利得が無い |
| 寸法 | 幅3〜10m、奥行3〜10m、高さ2.3〜4.0m（一様） | 個室から会議室・教室までを覆う。高さは天井の実寸の範囲 |
| 残響時間 RT60 | 0.1〜0.7秒（一様） | 0.1は家具の多い小部屋、0.7は硬い床の広い部屋。1秒を超える響きは Common Voice のような自宅録音では現れにくく、話速の手掛かり（数十〜数百ミリ秒の変化）を潰しすぎる |
| 吸音率 | `pyroomacoustics.inverse_sabine(rt60, room_dim)` で決める（全壁一様） | Sabineの式の逆算。寸法とRT60を決めれば吸音率は従属する |
| 鏡像法の次数 | `inverse_sabine` の推奨値と **12** の小さい方 | 上限を置かないと広い部屋・長いRT60で反射数が爆発し、生成に数百ミリ秒かかる。12でも応答は数千点あり、初期反射と初期減衰は十分に表現できる |
| 音源・マイクの位置 | 各壁から0.5m以上離して一様に無作為 | 壁に貼り付いた配置を避ける |
| 正規化 | 応答の絶対値の最大が1 | 残響をかけても全体の音量が大きく変わらないようにする |
| 実現できないRT60 | 吸音率が1を超える組み合わせは、単位インパルス（無響）を返す | 例外で学習を止めないため |

**畳み込みの際に長さと時刻を保つ**（`apply_reverb`）。素朴に畳み込むと
(1) 直接音が応答の先頭からの遅れ（伝搬遅延＋pyroomacousticsの補間フィルタ分）だけ
後ろにずれ、(2) 末尾に残響の尾が伸びて音声長が変わる。どちらも
「窓に含まれるモーラ数」という正解とずれる原因になるので、
応答の絶対値が最大の位置（直接音）が元の時刻に来るよう先頭を切り、元の長さで末尾も切る。
テストで、立ち上がりの時刻のずれが10ミリ秒未満であることを確かめている。

## 6. モーラ数が変わらないことの検証方法

docs/PLAN.md の完了条件は「各拡張について、適用前後でモーラ数のラベルが変わらないことを
確認する単体テスト」である。モーラ数は聴かないと数えられない（CLAUDE.md は試聴を禁じている）ので、
`tests/test_augment.py` では次の2つを機械的に確かめている。

1. **ラベルの読み替えが恒等であること**。`AugmentResult.mora_count` はどの拡張でも入力を
   そのまま返し、`mora_per_second` は時間伸縮以外では値を変えない
2. **モーラの数え上げに相当する量が保たれること**。音節を模した N 個のパルス列
   （正弦波の塊と無音の繰り返し）を作り、拡張の前後で短時間実効値の包絡から数えた
   塊の個数が N のまま変わらないことを確かめる。時間伸縮（0.7・1.0・1.5倍）、残響、
   音量変化、帯域制限、SN比15dB以上の雑音重畳で N が保たれることを確認済み

時間伸縮については加えて、
「モーラ数が不変」「毎秒モーラ数が `÷ stretch` になる」「実測した音声長から計算した
毎秒モーラ数が読み替え関数の値と一致する」の3点を検証している。

`test_no_time_direction_mask_is_provided` は、時間方向のマスクの API が
モジュールに存在しないことを確かめる（docs/spec.md の禁止事項を守り続けるための歯止め）。

## 7. 新規依存

**無し**。`librosa`（1.0.0）、`pyroomacoustics`（0.10.1）、`scipy`（1.18.1）は
すでに pyproject.toml の依存に入っており、`uv sync` 済みである。

## 8. 実行デバイス

拡張はすべて CPU（numpy / scipy / librosa）で行う。torch の演算は
メルの計算（CPU）だけであり、mps は経由しない。したがって
MPS未対応演算によるCPUフォールバックは発生しない。
