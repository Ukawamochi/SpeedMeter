# 推論時間の測定規則

実装は `src/spkrate/eval/latency.py`、入口は `scripts/measure_latency.py`、
テストは `tests/test_latency.py`（metrics.csv の列の移行は `tests/test_runner.py`）。

docs/spec.md の評価指標「1推論あたりの処理時間」の測り方を定める。docs/spec.md は変更していない。

## 0. 決めたことの一覧

| 項目 | 決定 |
| --- | --- |
| 測り方 | 比較対象の全モデルを**同一プロセス内で連続して**測る（1回の実行＝1測定セッション） |
| 1回の推論 | 2.0秒窓（32000標本）1つ: 対数メル計算 → 固定値の正規化 → テンソル化と転送 → モデルの前向き計算 |
| 同期 | 各回の計時の直前と直後に `torch.mps.synchronize()`（cpu は何もしない） |
| 入力 | 標準正規 × 0.05 の窓（種 20260921）。全モデルで同じ窓 |
| ウォームアップ | 各モデル20回（`--warmup`、既定 `DEFAULT_WARMUP`）。測定と同じ交互の順で行う |
| 測定回数 | 各モデル100回（`--repeats`、既定 `DEFAULT_REPEATS`） |
| 記録する統計量 | **中央値と最大値**（詳細 JSON には各回の値・平均・最小も残す） |
| 測定順 | **交互測定を採用**。周ごとに全モデルを1回ずつ、開始するモデルを1つずつずらす |
| 識別子 | `latency_session_id` = `lat-<ローカル時刻 YYYYmmddTHHMMSS>-<8桁の16進乱数>`。同じセッションの行は同じ値 |
| 比較 | 同じ `latency_session_id` の行の新方式の値だけを並べる。異なるセッションはエラー |

## 1. 1回の推論に含めるもの（旧方式とそろえた）

旧方式（`scripts/eval_dev_full.py` の `measure_latency` の `total_ms`、metrics.csv の
`latency_ms_per_inference`）と**同じ範囲**にした。

- 含める: 対数メル計算（CPU）、正規化、テンソル化と mps への転送、前向き計算、計時直後の同期までの時間
- 含めない: 音声の読み込み・再標本化

理由:

- 実運用では0.25秒ごとに2.0秒窓から対数メルを計算してモデルに通すので、待ち時間はメル計算を含む
- 範囲を旧方式にそろえると、旧方式との差が「プロセス・時刻」と「統計量（平均→中央値）」の違いだけになる

同期は、計時直前の同期で前回までの非同期の計算が残っていないことを保証し、計時直後の同期で
今回の計算の完了までを含める。旧方式は計時開始前に1回同期するだけで、200回の合計を回数で割っていた。
新方式は1回ごとに計時するので、前後の同期が要る。

## 2. ウォームアップ（既定20回）

mps では最初の数回にカーネル（シェーダ）の生成とメモリ確保が入り、遅くなる。これは数回で収まる。
既定は旧方式と同じ20回にした。数回で収まる初期化に対して十分な余裕があり、測定全体の時間もあまり増えない。
試測（3節）では、ウォームアップ直後の測定1回目（約1.85 ms）が中央値（約1.75 ms）の約1.06倍だった。
最大値（約1.90 ms）より小さいので、20回で足りると判断した。

## 3. 交互測定（採用）

モデルごとにまとめて測ると、発熱によるクロック低下、他のプロセス、メモリの状態など時間とともに
変わる条件が、測った順に偏って乗る。交互測定では周 r にモデル i を (i + r) mod n 番目に測る。
各モデルが各順位を同じ回数だけ経験し（周の数が n の倍数のとき）、時間変化がどのモデルにも均等に乗る。
ウォームアップも同じ順で行う。

- 不採用の案: モデルごとに連続して測る方式は比較用の `--no-interleave` として残した。
  無作為順は、同じ周の中で順位の偏りが残りうるので採らなかった。
- 注意: 交互測定では直前に別のモデルが動くので、キャッシュの状態は単独で連続実行したときと違う。
  測った値は「複数モデルが交互に走る条件での値」である。実運用で1モデルを連続して回す場合の絶対値とは
  少しずれうる。比較（相対値）を優先した。

## 4. results/metrics.csv の列

既存の列の**後ろ**に次の3列を足した。既存行の値と列の順は変えていない（新しい列は空欄）。
行末の種類（既存ファイルは `\n` と `\r\n` が混在）も行ごとに保った。
移行は `spkrate.eval.runner.upgrade_metrics_csv` で行う。
`append_metrics_row` は、列を足す前の形式の csv に追記しようとするとエラーにする。

| 列 | 意味 |
| --- | --- |
| `latency_session_id` | 測定セッションの識別子。精度評価の行と既存行は空欄 |
| `latency_ms_median` | 新方式の中央値（ミリ秒） |
| `latency_ms_max` | 新方式の最大値（ミリ秒） |

- 既存列 `latency_ms_per_inference` は**旧方式の平均**として残す。精度評価の入口（`eval_dev_full.py`、
  学習終了時の追記）は引き続きこの列に書く。行ごとに別プロセス・別時刻で測った値なので、**モデル間の比較には使わない**。
- 新方式の行は `split` を `latency_2s_window` とする。精度の指標列と `latency_ms_per_inference` は空欄。
  `model_size_bytes`・コミット・設定ファイルのパスは埋める。
- 比較の読み出しは `spkrate.eval.latency.compare_latency(csv, [実験ID...])` で行う。
  指定した全実験を含むセッションのうち最新のものを使う。そのようなセッションが無い場合（各実験の値が
  別々のセッションにしか無い場合）は `LatencySessionMismatchError` にする。
  `check_same_session` も、識別子が空（旧方式）の行や識別子の違う行が混ざるとエラーにする。

## 5. 精度評価との関係

- 精度評価（`scripts/eval_dev_full.py`: dev・dev_noisy）と推論時間の測定（`scripts/measure_latency.py`）は
  別の入口にした。精度評価の行には旧方式の時間が入るが、それは参考値である。
- **比較に使う推論時間は、比較対象の全モデルを1回の `measure_latency.py` で測った、
  `latency_session_id` 付きの新方式の値（中央値・最大値）に限る。**
- 比較対象のモデルが増えたら、既存のモデルも含めて全部を1つのセッションで測り直す
  （過去のセッションの値と並べない）。

## 6. 試測（results/metrics.csv には書いていない）

runs/exp001（005-first-model）と runs/exp002（007-augmentation）の checkpoint_best.pt を、
同じセッション `lat-20260924T184219-eefb3dec` で測った（mps、ウォームアップ20回、100回、交互測定、
CPU フォールバック0件）。出力先は作業用の一時ディレクトリの csv と JSON。

| 実験 | 中央値 (ms) | 最大値 (ms) | 平均 (ms) | 旧方式 `latency_ms_per_inference` (ms) |
| --- | --- | --- | --- | --- |
| 005-first-model | 1.749 | 1.898 | 1.751 | 1.746 |
| 007-augmentation | 1.744 | 1.885 | 1.748 | 4.190 |

同じ構造の2モデルが、新方式ではほぼ同じ値になった。旧方式では2.4倍の差がついていた。
旧方式の 007-augmentation の値は、runs/exp002/eval_dev_full.json によると dev 全件の評価に続けて
別のプロセス・別の時刻（2026-09-24 17時台）に測ったものである（前向き計算のみで 3.26 ms）。
差の原因は特定していない。いずれにせよ、別セッションで測った値を比べると測定条件の差が混ざる例になっている。
