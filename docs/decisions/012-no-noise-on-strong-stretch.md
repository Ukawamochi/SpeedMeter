# 強く縮めた窓に雑音を重ねない（exp019。docs/directives/2026-09-30.md タスク2）

- 判定日: 2026-09-30
- 読んだ資料: `CLAUDE.md`、`docs/directives/2026-09-30.md`、`docs/experiments/014-fast-playback.md`（2.3節）、`docs/experiments/013-fast-speech.md`（5.3節）、`docs/spec.md`（「データ拡張」、方式Bの窓と正解）、`docs/decisions/006-augmentation.md`、`docs/decisions/011-fast-window-sampling.md`、`src/spkrate/data/augment.py`、`src/spkrate/train/method_b.py`、`src/spkrate/train/train.py`、`configs/exp016.yaml`
- `configs/splits/test.json` は使っていない。音声を聴く判断はしていない

## 1. 目的

014 2.3節で、exp015〜exp018 の雑音下の悪化は主に雑音下での過大と分かった。013 5.3節4の推測は「強く縮めた窓が増え、雑音の時間変化を速さと取り違えるようになった」である。強く縮めた窓（伸縮率0.7未満）に雑音を重ねない学習（exp019）で、この推測を直接確かめる。

## 2. 決めたこと

| 項目 | 決定 |
| --- | --- |
| 設定のキー | `augment.params.noise_skip_stretch_below`（`AugmentConfig`）。`null`（既定）で無効。値は 0 より大きく 1 以下（1 を超えると伸縮しない音声まで省くので認めない） |
| 規則 | 伸縮率（長さの倍率）が閾値**未満**の音声には、雑音重畳の抽選に当たっても雑音を足さない。閾値ちょうどの音声には従来どおり重ねる |
| exp019 の値 | `noise_skip_stretch_below: 0.7`（指示書の「0.7未満」） |
| 判定に使う伸縮率 | 方式B: 窓の伸縮率（速い窓の選び直しの後の値。`WindowPlan.stretch`）。`augment_waveform(..., applied_stretch=plan.stretch)` で渡す。方式A: `augment_waveform` の中で引いた伸縮率（`applied_stretch` との積） |
| 変えないもの | 閾値以上の音声への雑音の確率（0.5）・SNR の範囲（0〜20dB）・雑音源（MUSAN noise の学習用）、雑音以外の拡張（残響・帯域制限・音量・周波数マスク）、無音・雑音のみのサンプル（元から拡張を掛けない）、窓の取り方（伸縮の抽選・伸縮率・位置・選び直し） |
| spec.md | 「データ拡張」に注を加えた（新しい実験の設定でだけ有効、既定は無効）。指示書タスク2の人間による仕様の運用の指示に基づく |

## 3. 乱数の扱い

**省く場合も、雑音重畳の抽選（`rng.random()`）・SNR（`rng.uniform`）・雑音の選択（`noise_source.sample`。ファイルの番号と切り出し位置）を同じ生成器から同じ回数だけ引き、結果だけを捨てる**方式にした。

理由:

- 抽選から雑音の選択までの乱数の消費を無効のときと完全に同じにできる。`fit_noise` の切り出し位置の抽選は雑音ファイルと抜粋の長さで有無が変わるので、回数を別途数えて空引きする方式は誤りやすい。`noise_source.sample` をそのまま呼べば同じになる
- 別の生成器を使う方式では、雑音の抽選そのものを主の生成器から外すことになり、無効のとき（exp016）の系列と揃えるには主の生成器の消費を別に再現する必要がある。同じ結果を得るのに複雑になる
- 代わりに、省いた窓でも MUSAN のファイルを読む（キャッシュに無ければ）。省くのは全窓の約8%（4節）で、雑音を重ねる窓の読み込みに比べて小さい

この結果、exp016 と exp019 で同じ種・エポック・番号の窓は、**省いた窓以外はビット単位で同じ**になり、省いた窓も雑音以外（帯域制限・音量・周波数マスク）の抽選と値は exp016 と同じになる（`tests/test_no_noise_strong_stretch.py` で、全0の雑音を足した場合と一致することを確かめた）。

音声を読まずに窓の伸縮率を求め（`WindowTrainDataset.window_label`。学習と同じ生成器）、雑音の抽選は確率0.5の独立な抽選として見込んだ（無音の抜粋に足さない場合は数えない）。無音サンプルは含まない。

| 伸縮率0.7未満の窓 | 15.78%（伸縮した窓 49.6% のうち 31.8%） |
| 雑音を重ねる窓（exp016） | 約50.0% |

## 5. 集計（log.txt と metrics.jsonl）

方式Bのエポックの窓の集計（`WindowEpochStats`。無音サンプルを除く）に次を加えた。既存の項目の値は変えない。

- `window_noise`・`window_noise_rate`: 雑音を実際に重ねた窓の件数と割合（`augment_applied` に `noise`。無音の抜粋で足さなかった窓は含まない）
- `window_noise_skipped`・`window_noise_skipped_rate`: 規則で雑音を省いた窓の件数と割合（抽選に当たり、伸縮率が閾値未満だった窓。`augment_applied` に印 `noise_skipped`）
- log.txt の「窓の集計」の行の末尾に「雑音を重ねた窓=件数(割合) 雑音を省いた窓=件数(割合)」
- 学習開始時の拡張の一覧の雑音重畳の行に「伸縮率0.7未満の音声には重ねない（noise_skip_stretch_below）」（有効なときだけ）。学習前の適用率の見積もり（`estimate_application_rates`）も、方式Aの伸縮率で省く分を差し引く

exp016 の学習は新しい集計の前に行ったので、exp016 の値は4節の見込み（約50%）で並べる。同じ実装で exp016 の設定を学習し直せば実測できる（`window_noise_skipped` は0になる）。

## 6. 副作用の見込み（exp019 の読み方）

1. **速い窓の雑音の頑健さ**: 毎秒10以上の窓の約59%、12以上の約82%が伸縮率0.7未満なので、exp019 では速い窓の多くが雑音なしで学習される。雑音下の速い発話（評価2の雑音条件がある場合や実使用）で追従が弱まる恐れがある。雑音下の過大が減っても、雑音下の高速度域の過小が増えていないかを確かめる
2. **「雑音がある＝遅い」の手がかり**: 雑音の有無が伸縮率（したがって正解の速さ）と相関するようになる。モデルが「雑音があれば低く出す」ことを覚えると、雑音下の出力が全体に下がる（過小に振れる）可能性がある。雑音下の偏りが exp005・exp007 の範囲（−0.02 前後）を超えて負に振れていないかを見る
3. **雑音を重ねる窓の割合の低下**: 全体で約50%→約42%。雑音下の精度そのものが、推測の検証と別に、雑音の学習例の減少で悪化する可能性がある。014 2.3節2のとおり出力の高さは学習ごとに揺れるので、1回の学習の差は揺れ（clean の偏り 0.022、正解0の窓の雑音下まとめ 0.072）と比べて読む
4. **clean の精度**: 雑音を省いた窓は clean の窓として学習されるので、clean の速い窓の学習例は増える。評価2（dev_fast）の clean の天井はわずかに上がる向きの可能性がある
5. **無音・雑音のみのサンプル**: 変えない（元から拡張を掛けない）。正解0の窓・MUSAN noise への出力は、雑音を重ねた遅い窓の学習例を通じて間接に影響を受けうる
6. **計算量**: 省いた窓でも雑音ファイルの読み込みと切り出しは行う（3節）。足し算と SNR の計算を省くだけなので、学習時間はほぼ変わらない
