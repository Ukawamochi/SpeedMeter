### 1.2 読み取れること

- **精度は書き起こしの圧勝**。全体で 3.2 分の1、どの帯でも 2.7〜3.7 分の1になる。音声認識は実際の音素列を同定しているので、音量の山の数という間接的な手がかりしか使わない包絡法とは情報量が違う
- **速度は包絡法の圧勝**。1,757倍の開きがある。包絡法は dev 全件29,518件を0.36分で処理したのに対し、書き起こしは同じ全件なら約6.08時間かかる見込みで、部分集合評価に切り替えざるを得なかった

## 2. 話速帯別に見た信号処理ベースラインの弱点

判断の材料として、dev の各帯の素性を `data/processed/clips.jsonl` と `configs/splits/dev.json` から集計した。
`const` は「常に dev の中央値 4.8544 と答える」自明な予測器のMAEである。

| 帯 | 件数（部分集合） | 件数の割合 | 帯の平均話速 | 帯の平均クリップ長 | 包絡法MAE | 相対誤差 | 書き起こしMAE | 相対誤差 | const |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 4未満 | 1,656 | 33.1% | 2.951 | 3.26秒 | 0.8297 | **28.1%** | 0.2245 | 7.6% | 1.904 |
| 4以上6未満 | 1,878 | 37.6% | 4.973 | 4.34秒 | 0.7483 | 15.0% | 0.2154 | 4.3% | **0.502** |
| 6以上8未満 | 1,133 | 22.7% | 6.889 | 6.16秒 | 0.8983 | 13.0% | 0.3377 | 4.9% | 2.035 |
| 8以上 | 333 | 6.7% | 8.931 | 6.25秒 | **2.1992** | **24.6%** | 0.7780 | 8.7% | 4.077 |
| 全体 | 5,000 | 100% | — | 4.52秒 | 0.9059 | — | 0.2836 | — | 1.557 |

（dev 全件でも構成はほぼ同じ：4未満 9,686件・平均2.934、4以上6未満 11,135件・平均4.959、6以上8未満 6,682件・平均6.878、8以上 2,015件・平均8.974。const は全体で1.557。）

弱点は2つあり、性質が異なる。

### 2.1 弱点A: 8以上の帯で絶対誤差が突出する（2.1992）

- 他の3帯（0.75〜0.90）の **2.4〜2.9倍**。全体MAE 0.9059 のうち 0.1465（**16.2%**）を、件数比 6.7% のこの帯だけで出している
- 原因は換算係数が固定であること。包絡法は音節数に `mora_per_syllable = 1.5278` を掛けてモーラ数にするが、話速が上がると隣接するモーラが1つの音量の山にまとまり、検出される山の数が話速に対して頭打ちになる。山の数が飽和する一方で係数は一定なので、速い話速ほど系統的に過小評価する（`results/envelope_baseline_tuning.md` の最終評価節も同じ診断）
- この帯が学習データでも少数である点が事態を悪くする。`results/clip_filtering.md` の分布では毎秒8モーラ以上は 13,706件／295,179件 = **4.6%** しかない。包絡法はパラメータを検証セット全体のMAE最小で選んでいるため、**件数の多い中央の帯に最適化され、少数の速い帯が切り捨てられる**という構造になっている。書き起こしベースラインでもこの帯だけ 0.7780 と他帯の2.3〜3.6倍になっており、帯の難しさ自体は共通だが、包絡法の悪化幅のほうがはるかに大きい

### 2.2 弱点B: もっとも件数の多い 4以上6未満の帯で、自明な予測器より悪い

- この帯（37.6%、全帯で最多）では包絡法 0.7483 に対し、常に中央値と答えるだけの const が **0.502** である
- 注意: 帯は**正解値で定義される**ので、定数 4.8544 が内側にある 4以上6未満の帯では const が構造的に有利であり、帯別に const と比べること自体は公平ではない（全体では包絡法 0.9059 対 const 1.557 で、包絡法が42%削減している）
- それを踏まえてなお、この数値は**最頻の話速帯において包絡法が正解値の位置をほとんど決められていない**ことを意味する。言い換えると、包絡法の全体MAEの良さは「端の帯（4未満・8以上）で中央から離れていることを言い当てている」ことで稼いでおり、中央帯での分解能は無いに等しい。一方の書き起こしはこの帯で 0.2154 と const の 2.3分の1であり、中央帯でも正解値を追えている

### 2.3 弱点C: 4未満の帯は相対誤差で最悪（28.1%）

- 絶対値では 0.8297 と目立たないが、帯の平均話速が 2.951 なので**相対誤差28.1%は全帯で最悪**である。「毎秒3モーラ」を「毎秒3.8モーラ」と表示する水準で、表示値としては使えない
- この帯はクリップ長の平均が3.26秒ともっとも短いのに話速が低い。つまり**無音・間が占める割合が大きい**。包絡法は無音閾値 `silence_floor_db = -20.0` で無音を除いているが、この閾値は全体のMAEを最小化する値として選ばれており（`results/envelope_baseline_tuning.md` の探索では -20 から外すと急激に悪化する）、間の多い発話に個別に合わせてはいない。呼気段落の切れ目の小さな山を音節として数えるか落とすかで誤差が直接動く帯である

### 2.4 まとめ

包絡法の誤差は「全帯に一様に散らばった雑音」ではなく、**端の2帯（8以上は絶対値、4未満は相対値）に偏っており、かつ最頻の中央帯では分解能がない**。
したがってモデルに求めるのは、全体MAEを少し下げることではなく、**この帯ごとの偏りを解消すること**である。目標値を帯別に置く理由がここにある。

### 3.3 目標値をこう引いた根拠

**（a）どこに線を引くかの構図**

書き起こしは MAE 0.2836 と正確だが 1推論851.7ミリ秒で、仕様（推論間隔0.25秒、ブラウザ上で常時動作）を根本的に満たさない（4章）。
包絡法は 0.4847ミリ秒と十分に速いが MAE 0.9059 で、中央帯では自明な予測器と大差ない（2.2節）。
モデルの役割は**この2つの間を埋めること**であり、目標値は「書き起こしに近い精度を、包絡法に近い速度で」という構図のどこに立つかを決める作業になる。

**（b）書き起こしと並ぶことは要求しない**

書き起こしは語彙知識を使って音素列そのものを同定している。長音「ー」・促音「ッ」・撥音「ン」がそれぞれ1モーラという仕様のモーラ定義は、
音響的には「母音の伸び」「無音区間」「鼻音」でしかなく、**語として同定しないと数えられない量を含む**。
2.0秒の文脈しか持たず書き起こしも行わない小型CNNに、この部分での同等は求められない。したがって**書き起こしの値（0.2836）を目標にはしない**。

**（c）包絡法を「わずかに上回る」ことも認めない**

モデルは包絡法より2桁重く（4章の予算で約47倍）、学習データ・学習時間・ONNX書き出しという工程一式を必要とする。
これに見合うには、包絡法との差が誤差範囲でなく構造的である必要がある。**包絡法と書き起こしの差を、どの帯でも6割以上詰める**ことを最低線とした。上表の目標値はいずれも 59.7〜65.4% を満たす。

**（d）帯ごとの水準は「表示値としての相対誤差」で決めた**

仕様の出力は毎秒モーラ数の表示であり、利用者が気にするのは絶対値の誤差ではなく相対的なずれである。そこで帯の平均話速に対する相対誤差で水準を置いた。

- **中央の2帯（4以上6未満・6以上8未満、合わせて60.2%）は相対8%**。4.973 mora/s に対し ±0.40、6.889 mora/s に対し ±0.55 にあたる。話速の表示刻みを 0.5 mora/s と考えると、この帯では概ね表示1刻み以内に収まる水準である。ここは件数が多く、話速も安定していて、包絡法の弱点B（分解能がない）を潰す必要がある帯なので、もっとも厳しく置く
- **端の2帯（4未満・8以上）は相対15%**。理由は2つ。第一に、8以上の帯は dev の6.7%・学習データの4.6%しかなく、平均への回帰による過小評価を完全には除けない。第二に、4未満の帯は無音と間の占める割合が大きく、クリップ全体の毎秒モーラ数という正解値そのものが「発話していない時間」に強く依存する（2.3節）。どちらも、データ量とラベルの性質からくる困難であり、中央帯と同じ水準を課すのは根拠がない

**（e）全体のMAE 0.50 は帯別目標よりわずかに厳しく置いた**

上の帯別目標値を件数で重み付けすると 0.514 になる。全体の目標 0.50 はこれより 0.014 厳しい。
これは意図したもので、**全帯でぎりぎり通る**モデルを合格にしないためである。件数の多い中央2帯のどこかで目標値に余裕を持つことを要求する。
5-4 では帯別5つと全体1つの計6つを**すべて**満たした場合のみ「目標到達」と判定する。

**（f）ラベル自体の誤差が作る下限との関係**

`docs/experiments/001-mora-label-quality.md` の測定は JSUT で相対誤差0.35%、毎秒モーラ数に換算して平均 **0.025 mora/s** である。これは上の目標値の 5% 未満で、平均値で見る限り無視できる。
ただし同文書が明記するとおり、**これは下限にすぎない**。測定したのは「原文 → モーラ数」の変換精度であって、「音声で実際に発話されたモーラ数」とのずれ（読み間違い・言い直し・言い淀み・フィラー・途中切れ）は一切測っていない。Common Voice は不特定多数の録音なのでこの成分は小さくない。

本段階のデータからその大きさを推し量る手がかりが1つある。**書き起こしベースラインの 0.2836 には、書き起こしの誤りだけでなくラベル雑音が含まれている**。話者が原文と違うことを言った場合、音声を聴いている書き起こしのほうが正しく、原文由来の正解のほうが誤っているが、評価上は書き起こしが罰せられるからである。
したがってこのラベルに対して到達しうる下限は **0.025 より大きく、0.2836 より小さい**どこかにあり、現時点で値を特定できない。

この不確かさは本段階の判定には影響しない。目標値 0.50 は考えうる下限の 2 倍近く上にあり、下限がどこであっても達成可能性は変わらないからである。
ただし次の歯止めを置く。**モデルのMAEが 0.35 を下回った場合、残差をモデルの不足として扱ってはならない**。その時点で残りの誤差はラベル雑音と区別できず、目標値をさらに下げる意味がない。第6段階6-3の聴取でラベル雑音の大きさが判明するまで、目標値を本節の数値より厳しくしない。

### 3.4 評価の単位が窓とクリップで違うことの影響

ベースライン2つは**クリップ1件につき1つの推定値**を出し、クリップ全体の毎秒モーラ数（総モーラ数 ÷ クリップ長）と比べている。
一方モデルの推論単位は2.0秒窓で、0.25秒ごとに1つの値を出す。この差は目標値の解釈に3つの影響を与える。
第一に、**クリップ単位の評価は窓単位の誤差を平均して薄める**。dev のクリップは平均4.52秒（6以上8未満の帯では6.16秒）で、重ならない窓に換算して2〜3個ぶんある。窓ごとの誤差が独立で偏りがなければ、クリップ平均のMAEは窓単位の 1.4〜1.7分の1程度になる。つまり**クリップ単位で 0.50 を満たすモデルの窓単位のMAEは 0.7 前後でありうる**。
第二に、**クリップ全体の毎秒モーラ数は、個々の窓の正解値ではない**。前後の無音や文中の間を含んだ平均値なので、間の中にある2.0秒窓の真の話速は 0 に近く、クリップ平均から大きく外れる。この差をどう扱うか（窓ごとのラベルを与えるか、窓の出力をクリップ単位に集約してから比べるか）は第4段階の設計事項であり、本節の目標値は**集約後のクリップ単位の値**に対するものである。
第三に、したがって**本節の目標値は必要条件であって十分条件ではない**。仕様が表示するのは窓ごとの値なので、クリップ単位の目標に到達しても、0.25秒ごとの表示が使い物になるかは別問題である。それは第9段階9-3（文単位の実環境評価）で確かめる。

## 4. 処理時間の上限

### 4.1 仕様から導く実時間の制約

仕様は「固定長窓2.0秒」「推論間隔0.25秒」「ブラウザ上で常時動作」である。ここから次が出る。

| 段階 | 値 | 導出 |
| --- | ---: | --- |
| 1推論あたりの実時間の限界 | **250 ミリ秒** | 推論間隔0.25秒。これを超えると次の推論に間に合わず、0.25秒間隔そのものが守れない |
| 1サイクルで使ってよいCPU時間 | **50 ミリ秒** | 常時動作するため、1スレッドを占有してはならない。占有率の上限を20%と置いた。残り80%はマイク入力のWeb Audio処理・描画・ページ本来の処理に残す |
| うち特徴量計算 | 10 ミリ秒 | 対数メルスペクトログラム。2.0秒窓は200フレームだが、0.25秒ごとの更新では25フレームぶんの増分計算で足りる |
| うちモデル推論（ブラウザ, wasm） | **40 ミリ秒** | 50 − 10 |
| うちモデル推論（ネイティブ換算） | **10 ミリ秒** | ONNX Runtime Web（wasm, 単一スレッド）は同じ機械のネイティブ ONNX Runtime CPU より概ね2〜4倍遅い。安全側の4倍を採り 40 ÷ 4 |

### 4.2 達成判定に使う数値

第8段階8-3（ONNX Runtime で2.0秒窓1回の推論を100回測定）に対する上限を次とする。

| 項目 | 上限 |
| --- | ---: |
| 1推論の平均（int8量子化後） | **10.0 ミリ秒** |
| 1推論の最大（int8量子化後） | **20.0 ミリ秒** |
| 1推論の平均（量子化前） | **20.0 ミリ秒** |
| モデルのファイルサイズ（int8量子化後、補助） | **5 MB** |

- 最大を平均の2倍に置いたのは、実行環境の揺れ（スケジューリング、メモリ確保）を見込んだものである
- 量子化前に 20.0 ミリ秒を置くのは、量子化が失敗した場合や量子化で精度が落ちすぎて採用できない場合に、量子化前のまま出せる余地を残すためである
- ファイルサイズはページ読み込みごとに転送されるため 5 MB を上限とした。10 Mbps の回線で約4秒にあたる。ベースライン2つは `results/metrics.csv` の `model_size_bytes` が空なので比較対象がない（包絡法はモデルを持たず、書き起こしは外部の重み約484MBを使う。後者はブラウザに載せる対象ですらない）

### 4.3 書き起こしベースラインと比べてどれだけ軽くする必要があるか

書き起こしベースラインの 851.68 ミリ秒はクリップ1件あたりの値で、部分集合の平均クリップ長は 4.522 秒である。2.0秒窓1回あたりに直すと次になる。

| 手法 | 測定値（クリップ1件） | 2.0秒窓1回あたりの換算 | 250ミリ秒の制約に対して |
| --- | ---: | ---: | --- |
| 書き起こし | 851.68 ミリ秒 | **376.7〜851.7 ミリ秒** | **満たさない（1.5〜3.4倍の超過）** |
| 包絡法 | 0.4847 ミリ秒 | 0.214 ミリ秒 | 余裕で満たす |
| モデルの上限（本節） | — | 10.0 ミリ秒 | 満たす |

換算に幅があるのは、Whisper の符号化器が入力を30秒に詰めて処理するため、**窓を短くしても処理時間が長さに比例して減らない**からである。376.7ミリ秒は所要時間がクリップ長に比例すると仮定した楽観的な下限、851.7ミリ秒は実測値をそのまま使った現実的な値である。

**結論として、モデルは書き起こしベースラインより 38倍から85倍軽くする必要がある。**
逆向きに見ると、モデルは包絡法（2.0秒窓あたり0.214ミリ秒）に対して **47倍まで重くてよい**。この幅が、3章の精度目標を達成するために使える計算量である。

なお重要なのは、書き起こしベースラインが「遅くて不便」なのではなく、**仕様の要件を原理的に満たさない**という点である。Apple Silicon のネイティブ実行、8プロセスの並列復号という有利な条件のもとでも、1推論が250ミリ秒の予算を超えている。ブラウザの wasm 実行ではさらに数倍遅くなる。したがって書き起こしベースラインは「精度の参照点」としてのみ意味を持ち、実装の選択肢ではない。
